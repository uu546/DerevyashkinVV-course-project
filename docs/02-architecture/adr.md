# Архитектурные решения (ADR)

**ADR (Architecture Decision Record)** - документирование ключевых архитектурных решений, их контекста, последствий и альтернатив.

---

## ADR-1: Выбор архитектурного паттерна

### Контекст

Необходимо выбрать архитектурный паттерн для реализации системы управления складом, который обеспечит:

- разделение ответственности;
- тестируемость;
- возможность масштабирования;
- поддержку веб-траектории.

### Рассмотренные альтернативы

| Альтернатива | Описание | Причины отказа |
|--------------|----------|----------------|
| **Трёхуровневая архитектура** | Presentation, Business Logic, Data Access | Недостаточная детализация, смешение бизнес-логики и контроллеров, сложность тестирования. |
| **Микросервисная архитектура** | Каждая бизнес-функция — отдельный сервис | Избыточно для масштаба проекта (6 месяцев, 1.5 млн руб), сложность развёртывания и мониторинга. |
| **Чистая архитектура (Clean Architecture)** | Независимость от фреймворков, внешних систем | Требует больше «обвязочного» кода (интерфейсы, адаптеры). |

### Принятое решение

**Использовать архитектурный паттерн PCMEF** (Presentation, Control, Mediator, Entity, Foundation) в веб-траектории.

### Обоснование

1. **Чёткое разделение ответственности** — каждый слой решает строго свою задачу.
2. **Управляемое направление зависимостей** — зависимости только сверху вниз (P → C → M → E → F).
3. **Тестируемость** — возможность изолированного тестирования каждого слоя с моками.
4. **Адаптируемость под Web** — естественное разделение на клиент (P) и сервер (C/M/E/F).
5. **Масштабируемость** — монолит может быть разбит на микросервисы по границам слоёв.

### Последствия

- **Плюсы:** Высокая поддерживаемость, тестируемость, слабая связанность.
- **Минусы:** Увеличение количества классов (интерфейсы + реализации).

## ADR-2: Распределение слоёв для веб-траектории

### Контекст

Система должна быть доступна через браузер, с централизованным хранением данных на сервере.

### Рассмотренные альтернативы

| Альтернатива | Описание | Причины отказа |
|--------------|----------|----------------|
| **Толстый клиент (Desktop)** | Вся логика на клиенте | Не подходит для веб-доступа, сложность обновлений. |
| **Тонкий клиент + сервер** | P на клиенте, остальное на сервере | Выбрано. |

### Принятое решение

- **Presentation (P)** — в браузере (Angular)
- **Control (C)** — на сервере (Spring Boot REST Controllers)
- **Mediator (M)** — на сервере (Spring Services)
- **Entity (E)** — на сервере (JPA Entities)
- **Foundation (F)** — на сервере (Spring Repositories)

### Обоснование

- Централизованное хранение данных и бизнес-логики.
- Доступ с любого устройства через браузер.
- Упрощение развёртывания и обновлений.

### Последствия

- **Плюсы:** Кроссплатформенность, централизация, безопасность.
- **Минусы:** Зависимость от сети, дополнительная задержка на HTTP-запросы.

## ADR-3: Выбор технологии для Presentation слоя

### Контекст

Необходимо выбрать технологию для реализации клиентской части.

### Рассмотренные альтернативы

| Альтернатива | Описание | Причины отказа |
|--------------|----------|----------------|
| **React** | Библиотека для построения пользовательских интерфейсов от Facebook | Высокая гибкость, но требует выбора дополнительных библиотек для маршрутизации, управления состоянием и работы с формами, что увеличивает сложность настройки проекта с нуля. |
| **Angular** | Полноценный фреймворк от Google | **Выбрано** |
| **Vue.js** | Прогрессивный фреймворк с низким порогом входа | Меньше распространён в корпоративной среде и образовательных программах. |

### Принятое решение

**Использовать Angular.**

### Обоснование выбора Angular

| Преимущество | Описание |
|--------------|----------|
| **«Всё включено»** | Angular предоставляет встроенные решения для маршрутизации (`Router`), HTTP-запросов (`HttpClient`), форм (`ReactiveForms`), что ускоряет разработку и не требует выбора и настройки десятка сторонних библиотек. |
| **TypeScript по умолчанию** | Статическая типизация помогает отлавливать ошибки на этапе разработки, улучшает автодополнение и рефакторинг, что особенно важно для проектов средней и большой сложности. |
| **Единообразие стиля** | Angular предлагает чёткую архитектуру (модули, компоненты, сервисы, DI), что упрощает поддержку кода несколькими разработчиками. |
| **Мощная CLI** | Angular CLI автоматизирует создание компонентов, сервисов, модулей, сборку и тестирование, что ускоряет разработку. |
| **Встроенный DI (Dependency Injection)** | Упрощает тестирование и повторное использование кода. |
| **RxJS** | Встроенная поддержка реактивного программирования для работы с асинхронными событиями и HTTP-запросами. |

### Последствия

- **Плюсы:** Быстрая разработка «из коробки», единообразие кода, хорошая тестируемость, отличная поддержка TypeScript.
- **Минусы:** Более тяжёлое приложение (размер бандла) по сравнению с React.

## ADR-4: Выбор технологии для бэкенда

### Контекст

Необходимо выбрать технологию для реализации серверной части.

### Рассмотренные альтернативы

| Альтернатива | Описание | Причины отказа |
|--------------|----------|----------------|
| **Spring Boot + Java** | Стандарт для корпоративной разработки | Выбрано. |
| **Node.js + Express** | JavaScript на сервере | Меньше типобезопасности, сложнее поддерживать большую кодовую базу. |
| **Python + Django** | Высокоуровневый фреймворк | Меньше производительность, не соответствует требованиям курса. |

### Принятое решение

**Использовать Spring Boot 3 (Java 17) с Spring Data JPA, Spring Security.**

### Обоснование

- Зрелая экосистема и большое сообщество.
- Встроенная поддержка JPA, Security, REST.
- Соответствие учебным требованиям (Java).

### Последствия

- **Плюсы:** Стабильность, документация, безопасность.
- **Минусы:** Более «тяжёлый» по сравнению с Node.js.

## ADR-5: Выбор стратегии аутентификации

### Контекст

Необходимо обеспечить безопасный доступ к системе с разграничением прав (USER / MANAGER).

### Рассмотренные альтернативы

| Альтернатива | Описание | Причины отказа |
|--------------|----------|----------------|
| **Session-based аутентификация** | Хранение сессии на сервере | Не подходит для REST API (stateless). |
| **JWT (JSON Web Token)** | Токен, хранящийся на клиенте | Выбрано. |
| **OAuth2 / Keycloak** | Внешний провайдер аутентификации | Избыточно для проекта. |

### Принятое решение

**Использовать JWT (Access Token only) без refresh token.**

### Обоснование

- Простота реализации.
- Stateless — не требует хранения сессий на сервере.
- Токен содержит роль пользователя для авторизации.

### Последствия

- **Плюсы:** Простота, масштабируемость.

## ADR-6: Выбор ORM-стратегии

### Контекст

Необходимо обеспечить взаимодействие с реляционной базой данных PostgreSQL.

### Рассмотренные альтернативы

| Альтернатива | Описание | Причины отказа |
|--------------|----------|----------------|
| **JPA / Hibernate** | Стандарт Java для ORM | Выбрано. |
| **JDBC (plain SQL)** | Прямая работа с SQL | Много шаблонного кода, сложность маппинга. |
| **MyBatis** | Полу-ORM с SQL-контролем | Меньше распространён, сложнее настроить связи. |

### Принятое решение

**Использовать JPA (Hibernate) с явным разделением на интерфейсы репозиториев и их реализации.**

### Обоснование

- Автоматический маппинг Entity ↔ Таблица БД.
- Управление связями (`@OneToMany`, `@ManyToOne`).
- Возможность писать сложные запросы через JPQL.

### Последствия

- **Плюсы:** Меньше кода, автоматическая генерация схемы.
- **Минусы:** Сложность оптимизации N+1 запросов (решается через `JOIN FETCH`).

## ADR-7: Выбор подхода к управлению зависимостями

### Контекст

Необходимо обеспечить внедрение зависимостей между слоями.

### Рассмотренные альтернативы

| Альтернатива | Описание | Причины отказа |
|--------------|----------|----------------|
| **Spring DI (IoC контейнер)** | Автоматическое внедрение через конструктор | Выбрано. |
| **Ручное внедрение (new)** | Явное создание объектов | Высокая связанность, сложность тестирования. |

### Принятое решение

**Использовать Spring IoC контейнер с внедрением зависимостей через конструктор.**

### Обоснование

- Слабая связанность.
- Упрощение тестирования (моки).
- Поддержка аннотаций (`@Service`, `@Repository`, `@Autowired`).

### Последствия

- **Плюсы:** Тестируемость, гибкость.
- **Минусы:** Нужно понимать механизмы Spring.
